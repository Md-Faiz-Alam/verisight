
# VeriSight Architecture

## 1. Overview

VeriSight is a Python-based autonomous AI data analyst.

Its architecture combines deterministic data processing, analytical SQL execution, controlled AI-assisted investigation, and structured analytical evidence.

The central design principle is:

> AI may plan and interpret analytical work, but deterministic components must validate and execute analytical queries.

VeriSight is designed to produce reproducible analytical observations and support evidence-grounded conclusions.

The system already implements the principal ingestion, profiling, quality, SQL execution, AI planning, repair, investigation, and synthesis components.

However, deterministic claim-level verification and comprehensive real-world analytical accuracy evaluation are not yet implemented.

Consequently, VeriSight should currently be understood as an advanced analytical engine under active development, not a fully validated autonomous analytical product.

---

## 2. Architectural Principles

### 2.1 Deterministic Before Generative

Deterministic components are responsible for:

- Dataset ingestion
- Source validation
- Schema inference
- Dataset profiling
- Data-quality evaluation
- Analytical SQL validation
- SQL execution
- Query-result construction
- Structured evidence preservation
- Serialization of supported domain objects

Generative components are responsible for:

- Translating analytical questions into proposed SQL
- Proposing investigation questions
- Producing bounded investigation decisions
- Proposing repairs for unsuccessful SQL
- Synthesizing analytical observations into conclusions

Generated instructions are not inherently trusted.

SQL generated by an LLM passes through VeriSight's analytical validation and controlled execution layers before its results become analytical observations.

This separation is essential to the project's architecture.

### 2.2 Stable Domain Contracts

Major subsystems communicate through explicit domain models.

Important contracts include:

- `LoadedTable`
- `LoadedDataset`
- Dataset schemas
- Column and table profiles
- Dataset profiles
- `QualityIssue`
- `DatasetAnalysis`
- `AnalysisSummary`
- `AnalysisInsight`
- `DatasetAnalysisResult`
- `QueryPlan`
- `QueryResult`
- `QueryExecution`
- `QueryObservation`
- `InvestigationDecision`
- `InvestigationState`
- `InvestigationResult`

Domain contracts should not be changed casually.

Changes must preserve established behavior or explicitly define and test a migration.

### 2.3 Evidence Before Conclusions

VeriSight separates observed analytical results from interpretations.

A SQL query produces a structured result.

When used by an autonomous investigation, the executed query and its result are preserved in a `QueryObservation`.

The synthesizer receives information about the investigation and its observations.

However, the current free-text conclusion is not independently verified claim by claim.

Evidence availability and evidence correctness are separate from conclusion correctness.

Future claim verification must preserve this distinction.

### 2.4 Preserve Source Meaning

Ingestion prioritizes fidelity over aggressive type coercion.

The implementation includes protections for:

- Significant leading zeros
- Large integer-like identifiers
- Nullable integers
- Nullable booleans
- Ambiguous source values
- Native Excel values
- Supported source encodings
- Missing-value representations

Inference must not silently introduce avoidable numerical precision loss.

Source-format limitations, including precision already lost in an Excel workbook, cannot always be repaired during ingestion.

### 2.5 Deterministic Dataset Identity

Display names and analytical SQL relation names are separate concepts.

A table retains a human-readable identity and receives a normalized relation identity.

Relation normalization prevents collisions between registered dataset tables and supports consistent downstream references.

Only authorized registered dataset relations may be referenced by supported analytical SQL.

### 2.6 Bounded Autonomous Execution

Autonomous investigation is not unlimited execution.

The implementation includes controls for:

- Maximum analytical steps
- Repeated analytical questions
- Failed query attempts
- Query repair
- Prompt budgets
- Incomplete evidence
- Resource limits
- Result-size limits

Bounded execution limits certain classes of failure but does not guarantee that every investigation will complete successfully.

### 2.7 Explicit External Data Disclosure

Default Gemini-backed generation requires configured credentials and explicit LLM data-disclosure permission.

Data-disclosure permission is an application-level authorization requirement.

It is not a substitute for dataset classification, provider security review, or deployment-specific privacy controls.

## 4. Data Ingestion Layer

**Package:** `verisight.ingestion`

The ingestion subsystem converts supported source files into normalized dataset structures.

Principal modules include:

```text
ingestion/
    dispatcher.py
    exceptions.py
    models.py
    schema.py
    service.py
    validation.py
    loaders/
        base.py
        csv.py
        excel.py
        json.py
```

### Responsibilities

- Validate input paths
- Select compatible loaders
- Read supported source formats
- Preserve source meaning
- Normalize table identities
- Infer structural schemas
- Construct loaded datasets
- Reject unsupported or invalid inputs

### Main Entry Point

`DatasetLoader` coordinates loading through format-specific components.

### CSV

CSV ingestion includes delimiter and encoding handling, source-value interpretation, and conservative numeric inference.

Particular care is required around large integers and identifier-like values.

### Excel

Excel ingestion processes supported workbook data and preserves native cell types where possible.

Nullable integer columns require special handling to prevent floating-point conversion from losing precision.

### JSON

JSON ingestion converts supported record structures into normalized tables.

It includes explicit handling for nullable integers, unsigned integers, oversized integers, and nullable boolean data.

### Boundary

The ingestion layer does not generate analytical conclusions.

Its responsibility is to deliver validated, normalized data to downstream components.

## 8. Analytical Execution Layer

**Package:** `verisight.execution`

This subsystem is implemented.

It is not a future architectural placeholder.

### 8.1 AnalyticalExecutionService

`AnalyticalExecutionService` provides the coordination layer for analytical execution.

Its responsibilities include:

- Constructing execution context
- Executing direct SQL
- Requesting query plans
- Validating generated plans
- Running planned queries
- Attempting bounded query repair where configured
- Returning structured results

The service exposes operations including:

- `execute()`
- `plan()`
- `run()`
- `ask()`

### 8.2 Query Planning

`QueryPlanner` is a protocol for translating an analytical request into a `QueryPlan`.

A plan contains an analytical question and proposed SQL.

The default Gemini-backed implementation is `GenerativeQueryPlanner`.

A generated query plan is not automatically considered correct.

It must pass the SQL validation and execution boundaries.

### 8.3 DuckDBExecutor

`DuckDBExecutor` executes analytical queries against registered dataset tables.

The implementation uses DuckDB.

Responsibilities include:

- Validating queries
- Determining authorized relation names
- Enforcing dataset relation restrictions
- Registering dataset tables
- Executing analytical SQL
- Limiting returned rows
- Enforcing configured execution resources
- Translating execution failures into domain exceptions

### 8.4 Query Results

`QueryResult` provides structured output containing column names and result rows.

`QueryExecution` associates an executed plan with its result.

These models allow downstream components to consume executed measurements rather than interpret raw database cursor objects.

## 9. SQL Security Boundary

The analytical execution layer applies multiple security controls.

### Analytical Query Validation

`AnalyticalQueryValidator` rejects unsupported query forms.

### Dataset Relation Validation

`validate_dataset_relations()` uses SQLGlot to inspect SQL structure and reject unauthorized relation access.

Its controls include restrictions on:

- Unregistered relations
- Schema-qualified relations
- Unsupported table functions
- Internal metadata access
- Unresolved SQL scopes
- Unsupported SQL source constructs

Supported CTEs and derived query scopes are considered during relation validation.

### DuckDB Restrictions

The engine includes controls for:

- External access
- Automatic extension installation
- Automatic extension loading
- Query memory consumption
- Temporary storage
- Execution time
- Result row count

The execution timeout applies to the controlled query execution section.

It should not automatically be interpreted as a wall-clock bound on the complete ingestion and dataset-registration lifecycle.

### Security Limitations

These controls reduce exposure.

They do not establish a complete hostile-query sandbox.

Before deploying to untrusted multi-user environments, additional requirements may include:

- Process isolation
- Operating-system resource limits
- Dataset access policies
- Concurrency controls
- Network restrictions
- Formal threat modeling
- Operational monitoring

Security controls should be extended in response to defined threats or reproducible vulnerabilities rather than speculative edge-case accumulation.

### 10.3 Structured JSON Investigation Responses

The Gemini structured JSON implementation was committed as:

`f7685a8 — feat: enable structured JSON for Gemini investigation`

It introduces an optional response JSON schema in `GeminiTextGenerationClient`.

The autonomous investigator uses a schema with these fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `action` | String enum | `investigate` or `finish` |
| `reasoning` | String | Reason for the proposed decision |
| `question` | String or null | Proposed analytical question |

The parser rejects malformed JSON, duplicate keys, invalid decision structures, and unsupported values.

SQL generation, repair, and final narrative synthesis continue using text responses.

## 11. Query Repair

**Relevant modules:**

```text
execution/
    repair.py
    generative_repair.py
    repair_prompting.py
```

SQL repair is a bounded recovery mechanism.

When a generated analytical query fails in a supported manner, the execution service may request a repaired plan.

The repairer receives information about the failed analytical request and produces a replacement query plan.

The replacement query remains subject to the established validation and execution controls.

The workflow does not support unlimited repair attempts.

The public facade also supports lazy creation of the default Gemini-backed repairer when configured.

Repair is not proof that a query is semantically correct.

A repaired query can execute successfully while still answering the wrong analytical question.

## 12. Autonomous Investigation

**Relevant modules:**

```text
execution/
    decisions.py
    investigator.py
    investigation.py
    investigation_result.py
    investigation_parsing.py
    investigation_prompting.py
    investigation_formatting.py
    investigation_compaction.py
    observations.py
    orchestration.py
    incomplete_evidence.py
```

### 12.1 Investigator

The investigator determines whether to:

- Request another analytical observation
- Finish the current investigation

The decision is represented by `InvestigationDecision`.

The default Gemini-backed implementation is `GenerativeInvestigator`.

### 12.2 InvestigationState

`InvestigationState` tracks the current state of an investigation.

It includes:

- Original analytical question
- Deterministic analysis
- Successful query observations
- Failed query attempts

The state exposes observation and failed-attempt counts.

It is used internally by orchestration and synthesis.

### 12.3 QueryObservation

A `QueryObservation` contains:

- `question`
- `sql`
- `result`

The SQL is the executed analytical plan associated with the observation.

The result contains structured returned data.

This contract provides provenance for analytical observations.

It does not directly link individual natural-language conclusion claims to their supporting observations.

### 12.4 InvestigationOrchestrator

`InvestigationOrchestrator` coordinates the bounded investigation.

Its principal loop is:

```text
Initialize InvestigationState
             |
             v
      Request decision
             |
       +-----+-----+
       |           |
       v           v
  Investigate    Finish
       |           |
       v           v
  Check limits  Check whether
  and repeats   observations exist
       |           |
       v           v
  Execute query  Synthesize conclusion
       |           |
       v           v
  Success/fail   InvestigationResult
       |
       v
  Update state
       |
       +----> Request next decision
```

The orchestrator handles:

- Maximum step enforcement
- Repeated-question detection
- Recording unsuccessful analytical attempts
- Successful observation collection
- Incomplete-evidence handling
- Prompt-budget failures where supported
- Final result construction

Not every provider failure is converted into an incomplete result.

Certain generation failures may propagate as application errors.

### 12.5 Incomplete Investigations

An investigation is marked incomplete when the workflow cannot establish a supported conclusion under its current rules.

Examples include:

- No successful analytical observations
- Maximum analytical steps reached
- Repeated analytical questions
- Evidence that cannot be fully evaluated within the prompt budget

The incomplete result preserves available successful observations where possible.

Its conclusion explicitly states that no analytical conclusion has been established.

### 12.6 InvestigationResult

`InvestigationResult` is a frozen dataclass.

It contains:

```python
question: str
conclusion: str
analysis: DatasetAnalysisResult
observations: tuple[QueryObservation, ...]
status: InvestigationStatus
```

It exposes `observation_count`.

The status values are:

- `complete`
- `incomplete`

The current public result does not include the complete internal failed-attempt history.

It also does not include structured claim-to-evidence verification results.

A `complete` status indicates completion according to the orchestration rules, not independently proven correctness of every conclusion claim.

## 14. Generative Synthesis

**Relevant modules:**

```text
execution/
    synthesis.py
    generative_synthesis.py
    synthesis_prompting.py
```

`InvestigationSynthesizer` defines the synthesis interface.

`GenerativeInvestigationSynthesizer` implements a Gemini-backed synthesis workflow through the text-generation contract.

Synthesis uses the investigation state to produce a natural-language conclusion.

The available state includes analytical observations and supporting investigation context.

However, the current synthesis stage does not include an independent deterministic validator of numerical claims.

For example, a generated conclusion might say:

> Category A represents 42% of total sales.

The current architecture can preserve the observations from which this value might be derived, but it does not yet require the conclusion to identify a specific evidence reference or pass a deterministic recomputation check.

This is a primary remaining architectural gap.

## 15. Evidence and Serialization

**Modules:**

```text
evidence.py

```

### 15.1 Structured Evidence

Evidence is a shared contract used across deterministic analytical findings.

The implementation validates and freezes supported nested evidence values.

It is intended to prevent downstream mutation of previously established analytical measurements.

### 15.2 Serialization

`to_jsonable()` provides JSON-compatible conversion for supported domain objects and values.

The serializer handles supported:

- Dataclasses
- Enums
- Paths
- Mappings
- Sequences
- Numeric values
- Temporal values
- Decimal values
- Missing-value representations

Serialization is kept separate from domain-model construction.

### 15.3 Current Provenance Boundary

The current system has two relevant evidence mechanisms:

1. Structured evidence associated with deterministic analytical findings.
2. `QueryObservation` records associated with executed SQL during autonomous investigation.

These mechanisms should be reused by a future claim-verification layer.

New verification functionality should not create an unrelated, competing evidence architecture without a demonstrated need.

## 16. Public Python Facade

**Module:** `verisight.service`

`VeriSight` provides the primary high-level application interface.

It exposes four workflows.

### analyze()

```python
result = VeriSight().analyze("data/orders.csv")
```

This workflow performs deterministic dataset analysis.

It returns `DatasetAnalysisResult`.

### execute()

```python
result = VeriSight().execute(
    "data/orders.csv",
    "SELECT COUNT(*) AS total FROM orders",
)
```

This workflow loads source data and executes validated analytical SQL.

It returns `QueryResult`.

### ask()

```python
result = VeriSight().ask(
    "data/orders.csv",
    "How many orders exist?",
)
```

This workflow uses a configured planner to generate and execute an analytical query.

It returns `QueryResult`.

### investigate()

```python
result = VeriSight().investigate(
    "data/orders.csv",
    "Investigate order amounts.",
    max_steps=5,
)
```

This workflow combines deterministic analysis, planning, analytical execution, investigation, and synthesis.

It returns `InvestigationResult`.

### Dependency Injection

The facade supports injection of compatible planner, investigator, synthesizer, and repairer components.

This enables deterministic tests and alternative component implementations without requiring a real Gemini API request.

The facade is not a substitute for a production HTTP API or user-interface layer.

## 20. Known Architectural Gaps

The following gaps remain material to product readiness.

### 20.1 Claim-Level Verification

The system does not yet independently validate individual numerical statements in generated conclusions against observed query results.

This is a planned capability.

### 20.2 Explicit Claim Provenance

The current `InvestigationResult` preserves successful query observations but does not provide structured claim-to-observation references.

### 20.3 Analytical Accuracy Benchmark

The existing automated suite primarily validates component correctness and controlled workflow behavior.

A benchmark with representative questions, known answers, and measurable analytical correctness is still required.

### 20.4 Real-Provider End-to-End Evaluation

The Gemini client and investigation parser have passed a live structured-output smoke test.

A complete live-provider investigation across ingestion, query planning, execution, repair, and synthesis remains to be evaluated systematically.

### 20.5 Resource Isolation and Scalability

In-memory ingestion and controlled SQL execution are suitable for the current development stage.

Large datasets, concurrent workloads, and hostile multi-user deployment require separate performance and isolation evaluation.

### 20.6 Product Interface

The project currently centers on its Python facade.

It does not yet provide a complete public CLI, HTTP API, reporting product, or graphical interface.

## 21. Next Architectural Milestone

The next product-defining milestone should be deterministic evidence-linked claim verification.

The proposed design is:

```text
InvestigationResult
        |
        v
Structured Analytical Claims
        |
        v
Explicit Evidence References
        |
        v
Deterministic Verification
        |
        +--> Supported
        |
        +--> Contradicted
        |
        +--> Unverifiable
        |
        v
Verification Results
        |
        v
Evidence-Grounded Conclusion
```

This design is proposed, not implemented.

### Initial Scope

The first version should focus on numerical claims whose evidence is explicitly available in returned analytical observations.

Examples include:

- Exact counts
- Sums
- Ratios
- Percentages
- Differences
- Comparisons supported by returned values

### Verification Rules

The implementation should:

1. Identify structured claims.
2. Associate each claim with explicit observation references.
3. Validate that referenced observations exist.
4. Recompute supported numerical claims deterministically.
5. Compare results using documented tolerances.
6. Distinguish supported, contradicted, and unverifiable claims.
7. Preserve the evidence used in verification.
8. Avoid presenting unverifiable claims as proven.

Verification should not consist solely of asking another language model whether the first model's answer looks correct.

### Evaluation Requirement

The verification milestone should include a small analytical acceptance benchmark with known expected answers.

The benchmark should measure:

- Query correctness
- Analytical answer correctness
- Numerical claim verification
- Evidence coverage
- Unsupported-claim frequency
- Incomplete investigation behavior

Implementation details and public API contracts must be finalized before introducing new production modules.

## 22. Architectural Direction

VeriSight has already implemented its principal data-analysis and autonomous-investigation layers.

The next architectural challenge is not to add more independent AI orchestration components.

It is to establish that conclusions produced by the existing system can be checked against the observations used to support them.

The intended progression is:

```text
Deterministic Analytical Foundation
                |
                v
Controlled SQL and AI Investigation
                |
                v
Structured Analytical Evidence
                |
                v
Deterministic Claim Verification
                |
                v
Measured Analytical Reliability
```
